# ARCHITECTURE — بنية المشروع

**الحالة:** تصميم مقترح، مرتبط بقرارين لم تُعتمدا بعد:
[ADR-0003](adr/ADR-0003-framework.md) (إطار العمل) و[ADR-0004](adr/ADR-0004-backend-data.md) (الخلفية والبيانات).
لا يُعتبر أي وصف في هذا الملف «مُختبرًا» حتى تُنفّذ المرحلة الأولى يتضمنه ويُقاس. راجع [ROADMAP.md](ROADMAP.md).

## 2. أجزاء المشروع

### 2.1 تطبيق العميل — قاعدة كود واحدة تُبنى لكل منصة

الهدف: وحدة واحدة للمنطق والواجهة، تُبنى خمس مرات: ويب، أندرويد، ويندوز، ماك، لينكس. هذا يقلّل الازدواجية ويحفظ اتساق التجربة، ويعتمد على قرار إطار العمل في [ADR-0003](adr/ADR-0003-framework.md).

يتألف من:

- **طبقة العرض**: شاشات عربية RTL، وكل نص يأتي من ملفات ترجمة.
- **طبقة المنطق المشتركة**:
  - نماذج البيانات: وصفة، مكوّن قابل للتحويل بين وحدات، خطوة، مستخدم، تعليق، اقتراح تعديل، قائمة تسوق.
  - محرك تحويل الكميات: إعادة حساب كل الكميات بتغيير عدد الأشخاص، مع قائمة وحدات ومكوّنات لا تتضاعف خطيًا تُنبه المستخدم صراحة. قواعد التحويل تُبنى كما في [ADR-0005](adr/ADR-0005-ingredient-search.md).
  - محرك تجميع التسوق: دمج مكونات عدة وصفات في قائمة واحدة دون تكرار، وتصنيف السطور إلى فئات.
  - محرك مطابقة المكونات: مقارنة قائمة المستخدم بمكونات الوصفات بعد المرور بقاموس المرادفات داخل الخلفية.
- **طبقة المنصة** (الجزء الذي يختلف بين الأنظمة):
  - نطق الصوت: واجهة واحدة في الكود، يتنفذها ما يوفره كل نظام — قرارها في [ADR-0006](adr/ADR-0006-voice-guidance.md).
  - تخزين محلي: «مكونات ثلاجتي» وقائمة التسوق الحالية تُخزَّن على الجهاز ولا تُرسَل للسيرفر إلا بموافقة المستخدم الصريحة.
  - عدّادات الخطوات الموقوتة: تُعالَج بعناية خاصة لكل منصة في مرحلتها (المرحلة 4)، ولا يُتجمَّل عنها شيء الآن.

### 2.2 الخدمة الخلفية — مخزن البيانات والحسابات

- **قاعدة بيانات علائقية (PostgreSQL)**: جداول للوصفات والمكونات والخطوات والمستخدمين والتعليقات والتقييمات واقتراحات التعديل. **مخطط القاعدة يُكتب كسكربت SQL داخل المستودع** (`db/migrations/`) حتى يبقى المخطط ملكًا للمشروع ويمكن إعادة بنائه على أي مزوّد.
- **صلاحيات على مستوى الصف (Row Level Security)**: كل جدول تحدد سياساته من يقرأ ومن يكتب؛ فلا أحد يعدّل وصفة غيره ولا يقرأ بيانات غيره.
- **الوصول من العميل مباشرة إلى قاعدة البيانات** عبر واجهة الاستعلام، دون سيرفر وسيط خاص بنا في المرحلة الأولى. إن احتجنا لاحقًا إلى منطق يعمل على السيرفر (إشعارات، فرز مسبق، آليات الإبلاغ عن المحتوى)، يُضاف بقرار ADR جديد.
- **تخزين الصور** بقواعد صارمة: نوع الملف (JPEG/PNG فقط)، حد أقصى للحجم، وفحص قبل القبول.

### 2.3 البحث — داخل قاعدة البيانات

الفهرسة النصية والتطابق تعمل داخل PostgreSQL (بحث نصي كامل + تقريب اسمي + قاموس مرادفات صغير). لا محرك بحث خارجي في المرحلة الأولى؛ إن أثبت القياس الحاجة له، يُكتب ADR جديد له.

## 3. مسارَان رئيسيان (كيف تتصل الأجزاء)

### أ. نشر وصفة
1. المستخدم يكتب الوصفة: مكونات موحّدة (كمية + وحدة) وخطوات مرقّمة.
2. التطبيق يفحص المدخلات محليًا (كميات موجبة ووحدات معروفة).
3. يُرفَع عبر HTTPS إلى الخلفية، تتحقق الصلاحيات وصورة الوصفة، ثم تُنشر للعموم.

### ب. البحث بالمكونات المتوفرة في الثلاجة
1. المستخدم يُدخل مكوناته؛ تُحفظ على جهازه فقط.
2. عند طلب الترشيح يُرسَل استعلام قراءة فقط إلى الخلفية.
3. الخلفية تطابق بعد قاموس المرادفات، وتعيد النتائج على درجتين: تطابق كاملًا ثم جزئيًا مع سطر «تنقصك: …».

## 4. حدود متعمّدة (نعرفها ونقبلها)

1. لا سيرفر وسيط خاص في المرحلة الأولى؛ تعقيد تشغيله مؤجَّل إلى مرحلة لاحقة.
2. لا تحليلات تجارية ولا خدمات من طرف ثالث تصل إلى بيانات المستخدم دون موافقة صريحة وقرار وثّق.
3. مزامنة «ثلاجتي» بين الأجهزة ميزة اختيارية لاحقة تُفعّل بموافقة صريحة لكل حساب.
