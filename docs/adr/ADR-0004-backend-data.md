# ADR-0004: الخلفية وطريقة حفظ البيانات والحسابات

- **الحالة:** مقبول — بموافقة المالك بتاريخ 2026-10-31
- **التاريخ:** 2026-10-31

## السياق

نحتاج قاعدة بيانات للوصفات والمستخدمين والتعليقات، ونظام تسجيل دخول، وتخزين صور، وصلاحيات صارمة. مع قرار ADR-0003 (لا سيرفر وسيط خاص في المرحلة الأولى) يتصل التطبيق بالخدمة الخلفية مباشرة. أصعب ميزة تقنيًا هي مطابقة المكونات، وهي أسئلة علائقية على جداول مترابطة.

## الخيارات

1. **Supabase أعلى PostgreSQL:** قاعدة علائقية كاملة، مع تسجيل دخول وتخزين ملفات وصلاحيات على مستوى الصف مدمجة مع مكتبة عملاء لكل منصة، ومفتوحة المصدر بطريقة تسمح بالنقل إلى مزود آخر.
2. **Firebase:** خدمات سريعة الجاهزية، لكن قاعدتها غير العلائقية أضعف في أسئلة المطابقة بين المكونات والوصفات، وهي خدمة مغلقة مرتبطة بالمزود.
3. **خلفية مبنية خصيصًا (مثل NestJS مع PostgreSQL):** تحكم كامل في كل شيء، لكنه يعني تشغيل وصيانة سيرفر آمن منذ اليوم الأول، ووقتًا أطول قبل أول ميزة مفيدة.

## التوصية

**Supabase** في المرحلة الأولى، مع ضمانات حماية من الارتباط بالمزود:

1. مخطط القاعدة يُكتب كسكربتات SQL في المستودع داخل مجلد `db/migrations/`، وكل تعديل مخطط في PR مستقل. لا يجوز تعديل الجداول عن طريق لوحة التحكم دون سجل في المستودع.
2. صلاحيات على مستوى الصف لكل جدول: الوصفات للقراءة العامة، وتعديل كل وصفة لصاحبها فقط، وبيانات كل مستخدم لصاحبها فقط.
3. تسجيل الدخول بالبريد وكلمة مرور مُدارَة بواسطة الخدمة الخلفية نفسها. تفاصيل سياسة كلمات المرور تُعتمد في المرحلة 1.
4. صور الوصفات تُخزَّن بقواعد صارمة: نوع ملف محدد، وحد أقصى للحجم، وفحص قبل القبول.
